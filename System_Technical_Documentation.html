1.3 MediatR CQRS Pipeline

MediatR-backed controllers and actions route operations through the following pipeline. Some legacy/direct API surfaces, such as EmployeeApiController and inventory verification endpoints, use ApplicationDbContext directly and do not pass through these behaviors.

#BehaviorFileResponsibility
1ValidationBehaviorValidationBehavior.csRuns FluentValidation validators; throws ValidationException on failure
2AuditLoggingBehaviorAuditLoggingBehavior.csCaptures command metadata (actor, IP, payload) into AuditLogs
3TransactionBehaviorTransactionBehavior.csWraps eligible *Command handlers in a database transaction; auto-rollback on failure
4RequestLoggingBehaviorRequestLoggingBehavior.csDebug/error logging around MediatR request handling
5PerformanceBehaviorPerformanceBehavior.csLogs slow requests exceeding a threshold

Code Example: ValidationBehavior.cs — Request Validation Gate

This behavior intercepts every MediatR request before it reaches the handler. It runs all registered FluentValidation validators in parallel and rejects the request if any rule fails.

public sealed class ValidationBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>    // MediatR cross-cutting concern interface
    where TRequest : notnull
{
    private readonly IValidator<TRequest>[] _validators;

    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,     // next() invokes the actual handler
        CancellationToken cancellationToken)
    {
        if (_validators.Length == 0)
            return await next();                      // No validators registered → skip

        var context = new ValidationContext<TRequest>(request);
        var results = await Task.WhenAll(             // Run ALL validators in parallel
            _validators.Select(v => v.ValidateAsync(context, cancellationToken)));

        var failures = results
            .SelectMany(r => r.Errors)
            .Where(e => e != null).ToList();

        if (failures.Count > 0)
            throw new ValidationException(failures);  // ❌ Returns 400 Bad Request

        return await next();                           // ✅ Proceed to handler
    }
}

Key Points:

  • IPipelineBehavior wraps the next() delegate, forming a chain identical to ASP.NET Core middleware.
  • Parallel validation via Task.WhenAll — returns all errors in one round-trip instead of fail-fast.
  • Zero-validator fast path — Query requests skip the validation context entirely.

Code Example: TransactionBehavior.cs — Automatic Transaction Management

Wraps eligible Command handlers in a database transaction. The PostCommitActionQueue ensures queued side effects only run after a successful commit.

public async Task<TResponse> Handle(TRequest request,
    RequestHandlerDelegate<TResponse> next, CancellationToken ct)
{
    if (!ShouldWrapInTransaction(request))       // Only *Command types
        return await next();

    await using var transaction =
        await _context.Database.BeginTransactionAsync(ct);
    try
    {
        var response = await next();                  // Execute handler
        await transaction.CommitAsync(ct);            // ✅ Commit
        await _postCommitActionQueue.FlushAsync(ct);  // Run queued side effects
        return response;
    }
    catch
    {
        _postCommitActionQueue.Clear();               // Discard pending side effects
        await transaction.RollbackAsync(ct);           // ❌ Rollback
        throw;
    }
}

// Convention: type name ending in "Command" → wrap in transaction
private static bool ShouldWrapInTransaction(TRequest request)
{
    var name = request.GetType().Name;
    if (!name.EndsWith("Command")) return false;
    if (name.Contains("Import")) return false;  // Imports manage own txn
    return true;
}

Key Points:

  • Convention-based: Transaction wrapping determined by the request type name suffix, keeping commands free of infrastructure concerns.
  • PostCommitActionQueue: Prevents "phantom" notifications from rolled-back operations.

1.4 Multi-Company Data Isolation

The system implements a logical multi-company (multi-tenant) architecture. Each user is associated with one or more companies via the UserCompany join table. Data isolation is enforced at the application layer:

Tenant Resolution & Scoping

  • UserCompany — Maps each ApplicationUser to one or more Company names
  • CompanyScopeHelper — Utility class that loads the current user's accessible companies from claims/DB and filters queries accordingly
  • Controller/Query-Level Enforcement — Company-scoped data is filtered through CompanyScopeHelper or ItAdminCompanyScopeSupport; individual record endpoints call CompanyScopeHelper.CanAccessCompany(User, branch) where branch-level checks are required
  • Dictionary Entities — Departments, Email Groups, Shared Mailboxes, Server Folders, and Software Licenses are linked to companies via join tables (e.g., DepartmentCompany, EmailGroupCompany)

Code Example: Stateless State Machine — OnboardingRequest.cs

The onboarding lifecycle is enforced by a Stateless finite state machine embedded in the domain model. It prevents invalid transitions (e.g., jumping from Draft to Completed) at the model level.

public class OnboardingRequest : ISlaTrackable
{
    // State machine is NOT persisted — rebuilt from Status on every load
    [NotMapped]
    private readonly StateMachine<RequestStatus, OnboardingTrigger> _machine;

    public OnboardingRequest()
    {
        _machine = new StateMachine<RequestStatus, OnboardingTrigger>(
            () => Status,             // Read current state from entity
            status => Status = status  // Write new state back to entity
        );
        ConfigureStateMachine();
    }

    public RequestStatus Status { get; set; } = RequestStatus.Draft;

    private void ConfigureStateMachine()
    {
        _machine.Configure(RequestStatus.Draft)
            .Permit(OnboardingTrigger.SubmitByHr,
                    RequestStatus.PendingITApproval)
            .Permit(OnboardingTrigger.Cancel,
                    RequestStatus.Rejected);

        _machine.Configure(RequestStatus.PendingApproval)
            .Permit(OnboardingTrigger.Cancel, RequestStatus.Rejected);

        _machine.Configure(RequestStatus.PendingHRApproval)
            .Permit(OnboardingTrigger.Cancel, RequestStatus.Rejected);

        _machine.Configure(RequestStatus.PendingHODApproval)
            .Permit(OnboardingTrigger.Cancel, RequestStatus.Rejected);

        _machine.Configure(RequestStatus.PendingITApproval)
            .PermitReentry(OnboardingTrigger.StartItSetup)
            .Permit(OnboardingTrigger.FinishOnboarding,
                    RequestStatus.PendingEmployeeSign)
            .Permit(OnboardingTrigger.Cancel,
                    RequestStatus.Rejected);
    }

    // Public trigger methods used by command handlers
    public void SubmitByHr()       => _machine.Fire(OnboardingTrigger.SubmitByHr);
    public void FinishOnboarding() => _machine.Fire(OnboardingTrigger.FinishOnboarding);
    public void Cancel()           => _machine.Fire(OnboardingTrigger.Cancel);

    // Check if a transition is allowed before rendering UI buttons
    public bool CanBeRejected() =>
        Status != RequestStatus.Rejected &&
        _machine.CanFire(OnboardingTrigger.Cancel);
}

How It Works:

  • [NotMapped]: The machine object is never persisted — only the Status enum is stored. The machine is reconstructed from the persisted status each time the entity loads from EF Core.
  • .Permit(trigger, target): Defines a valid transition. Attempting any other configured trigger throws InvalidOperationException, so command handlers cannot use the state-machine API to skip guarded steps.
  • .PermitReentry(): Allows IT to re-enter the same state when saving partial setup progress without changing status.
  • CanFire(): Used inside entity helper methods such as CanBeRejected(), which command handlers call before firing transitions.

1.5 Architecture Rationale & Design Decisions

This section explains why each major library and pattern was chosen, what problem it solves, and what the alternative would look like without it.

Why MediatR? — Decoupling Controllers from Business Logic

Problem: In a traditional MVC application, controllers contain business logic directly. As the system grows, controllers become bloated "god classes" — hundreds of lines mixing HTTP concerns (model binding, response formatting) with domain logic (validation, state transitions, database operations). This makes the code hard to test, hard to reuse, and hard to maintain.

Solution: MediatR implements the Mediator pattern combined with CQRS (Command/Query Responsibility Segregation). Instead of controllers calling services directly, they send a request object (Command or Query) to MediatR, which routes it to the correct handler.

// ❌ WITHOUT MediatR — Controller does everything
public class OnboardingController : Controller
{
    public async Task<IActionResult> Sign(int id, OnboardingSignatureApiRequest dto)
    {
        // Validation mixed into controller
        if (string.IsNullOrEmpty(dto.SignatureData)) return BadRequest();

        // Business logic in the controller
        var request = await _context.OnboardingRequests.FindAsync(id);
        request.ITAdminSignature = dto.SignatureData;
        request.Status = RequestStatus.PendingEmployeeSign;

        // Audit logging manually added
        _context.AuditLogs.Add(new AuditLog { ... });

        await _context.SaveChangesAsync();
        return Ok();
    }
}

// ✅ WITH MediatR — Controller only dispatches
public class OnboardingApiController : ControllerBase
{
    public async Task<IActionResult> Sign(int id, OnboardingSignatureApiRequest dto)
    {
        var result = await _mediator.Send(
            new ProcessOnboardingSignatureCommand(
                id, dto.SignatureType, dto.SignatureData));
        return Ok(result);
    }
}
// Validation, audit logging, and transactions happen
// automatically in the pipeline — the handler only
// contains the actual business logic.

Benefits in This System:

  • Single Responsibility: Each handler does exactly one thing. ProcessOnboardingSignatureCommand handles onboarding signatures. ProcessOnboardingRejectionCommand handles rejection. No mixing of concerns.
  • Cross-Cutting Concerns: Validation, audit logging, transaction management, and performance monitoring are applied to commands sent through MediatR — reducing duplicated infrastructure code across the 26 controller classes.
  • Testability: Handlers can be tested without MVC controller plumbing; database-backed handlers still need an EF test context or mocked dependencies.
  • Discoverability: New developers can search for *Command.cs and *Query.cs to find MediatR-backed operations without reading controller code.

Why Pipeline Behaviors? — The "Middleware for Business Logic" Pattern

Problem: Most mutating MediatR requests need input validation, audit logging, transaction wrapping, and performance monitoring. Without a pipeline, each handler would need to manually call these services — leading to duplicated infrastructure code and a higher risk of missed audit logs or transaction boundaries.

Solution: MediatR Pipeline Behaviors (IPipelineBehavior<TRequest, TResponse>) act as middleware for business logic. They wrap the next() delegate in a chain, just like ASP.NET Core HTTP middleware wraps RequestDelegate.

flowchart LR A["Controller\nsends Command"] --> B["ValidationBehavior\nCheck input rules"] B --> C["AuditLoggingBehavior\nRecord actor + payload"] C --> D["TransactionBehavior\nBegin DB transaction"] D --> E["RequestLoggingBehavior\nDebug/error log"] E --> F["PerformanceBehavior\nStart timer"] F --> G["Command Handler\nDomain logic"] G --> F F --> E E --> D D --> C C --> B B --> A style A fill:#dbeafe,stroke:#1e40af style G fill:#d1fae5,stroke:#065f46

Why This Matters:

  • Less boilerplate in handlers: Command handlers can focus on business logic while validation, command audit logging, transaction management, and performance timing are handled by the pipeline.
  • Consistent enforcement: Commands sent through MediatR pass through the globally registered pipeline; commands without validators use the zero-validator fast path, and audit logging applies to request types ending in Command.
  • Ordering matters: Validation runs first (no point starting a transaction for invalid data). Audit logging runs before the transaction (so failures are captured). Performance monitoring wraps the entire chain.

Why FluentValidation? — Declarative Input Validation

Problem: ASP.NET's built-in [Required] and [StringLength] data annotations are limited to simple property-level checks. Real business rules — like "department name must be unique" or "selected HOD must belong to the selected company" — require validation code that would otherwise clutter the model or controller.

Solution: FluentValidation provides a fluent, testable API for building complex validation rules in dedicated Validator classes. These validators are auto-discovered by the DI container and executed by the ValidationBehavior in the MediatR pipeline.

// Example: Validator for creating a department
public sealed class CreateDepartmentCommandValidator
    : AbstractValidator<CreateDepartmentCommand>
{
    public CreateDepartmentCommandValidator(ApplicationDbContext context)
    {
        RuleFor(x => x.Name)
            .Cascade(CascadeMode.Stop)
            .NotEmpty()
            .Length(2, 100)
            .MustAsync(async (name, ct) =>
                !await context.Departments.AsNoTracking()
                    .AnyAsync(d =>
                        d.Name.ToUpper() == name.Trim().ToUpper(), ct))
            .WithMessage("Department name must be unique.");

        RuleFor(x => x.Description).MaximumLength(500);
    }
}

Why Not Just Data Annotations?

  • Async rules: Data annotations cannot call async methods. FluentValidation supports MustAsync for database lookups (e.g., uniqueness checks).
  • Separation: Validation rules live in their own files, not cluttering the domain model or command class.
  • Conditional logic: When() and Unless() allow rules that only apply based on other properties — impossible with attributes.
  • Testability: Each validator can be unit-tested independently with TestValidate() — no HTTP request needed.
  • Pipeline integration: Validators for MediatR requests run automatically via ValidationBehavior. Legacy/direct MVC actions still use ModelState checks where they do not route through MediatR.

Why Stateless? — Domain-Driven Workflow Enforcement

Problem: Onboarding requests follow a strict lifecycle (Draft → PendingITApproval → PendingEmployeeSign → Completed). Without a state machine, this logic would be scattered across controllers as if/else chains — making it easy to introduce bugs like allowing a "Draft" request to jump directly to "Completed". Offboarding uses a separate multi-party approval flow described later in this document.

Solution: The Stateless library provides a lightweight finite state machine that is configured directly in the domain model. The machine defines which configured trigger transitions are legal. Illegal trigger calls throw InvalidOperationException, keeping handler-driven workflow changes on the allowed path.

// Without Stateless — fragile and error-prone:
if (request.Status == RequestStatus.Draft)
    request.Status = RequestStatus.PendingITApproval;  // What about validation?
else if (request.Status == RequestStatus.PendingITApproval)
    request.Status = RequestStatus.Completed;           // Skipped employee sign!

// With Stateless — transitions are declared, not coded:
_machine.Configure(RequestStatus.Draft)
    .Permit(OnboardingTrigger.SubmitByHr, RequestStatus.PendingITApproval);
// Trying to fire FinishOnboarding from Draft → throws InvalidOperationException

Why This Matters:

  • Business rules as code: The state machine IS the specification. Product managers can read .Permit() calls and understand the workflow without reading controller logic.
  • Guarded transitions: Command handlers that use the state-machine methods cannot skip configured workflow steps; the machine validates the trigger before allowing it.
  • Guard helper methods: Methods such as CanBeRejected(), CanBeItSigned(), and CanRegenerateToken() expose state checks used by handlers and UI flows before actions are allowed.
  • Self-documenting: The ConfigureStateMachine() method is a single source of truth for the entire workflow, replacing documentation that can go stale.

Why Argon2id? — Future-Proof Password Security

Problem: ASP.NET Identity's default password hasher uses PBKDF2 with HMAC-SHA256. While acceptable, PBKDF2 is vulnerable to GPU-based brute-force attacks because it is not memory-hard — an attacker with GPUs can compute millions of hashes per second cheaply.

Solution: Argon2id is the winner of the Password Hashing Competition (2015) and is recommended by OWASP. It is memory-hard (requiring 32 MB per hash), making GPU attacks economically impractical. The id variant combines Argon2i (side-channel resistant) and Argon2d (GPU-resistant) for defense-in-depth.

Why Not Just PBKDF2?

  • Memory hardness: Each Argon2id hash requires 32 MB of RAM. An attacker with 8 GB of GPU memory can only compute ~250 hashes in parallel — vs. millions with PBKDF2.
  • Transparent migration: The self-describing hash format allows upgrading parameters (memory, iterations) without resetting all user passwords. Old hashes are auto-upgraded on next login.
  • PDPA 2010 compliance: Malaysia's data protection law (Principle 4: Security) requires "reasonable steps" to protect personal data. Argon2id represents the current industry best practice.

Why HMAC-SHA256 for Signatures? — Cryptographic Integrity Guarantees

Problem (Audit Finding H-03): Digital signatures are stored as Base64-encoded images in the database. Without integrity verification, a database administrator could silently swap one signature image for another — creating a forged approval with no detection mechanism.

Solution: Every signature is accompanied by an HMAC-SHA256 hash computed over the complete signing context (entity type, ID, signer, timestamp, and the signature data itself). If any field is modified after signing, the HMAC verification fails.

Why HMAC and Not a Simple Hash?

  • HMAC uses a secret key: A simple SHA-256 hash can be recomputed by anyone. HMAC requires the configured server-side key — even a DBA with only database access cannot forge a valid HMAC without that key.
  • Canonical message format: The pipe-delimited format (EntityType|EntityId|Signer|Timestamp|Base64) ensures that all contextual data is bound to the signature. Moving a signature from Request #1 to Request #2 changes the EntityId, invalidating the HMAC.
  • Constant-time comparison: CryptographicOperations.FixedTimeEquals prevents timing attacks where an attacker could deduce correct HMAC bytes one-at-a-time by measuring response times.

Why Mapster? — High-Performance Object Mapping

Problem: The system has many entity-to-ViewModel mappings (e.g., OnboardingRequest → OnboardingIndexListItem). Manual mapping code is tedious, error-prone, and creates maintenance burden when properties are added.

Solution: Mapster auto-maps properties between objects by convention (matching property names). Compared to AutoMapper:

  • Performance: Mapster provides expression-based projection via ProjectToType and centralized mapping configuration, reducing manual projection code while keeping queries readable.
  • Zero config for simple cases: Matching property names are mapped automatically. Custom mappings are configured only when names differ.
  • Lightweight: The project uses Mapster plus Mapster.DependencyInjection for a small mapping package set.

Why Serilog? — Structured Diagnostic Logging

Problem: The built-in Microsoft.Extensions.Logging writes plain text logs that are difficult to search, filter, and analyze at scale. Finding "all failed login attempts from IP 172.16.3.50 in the last hour" requires fragile regex parsing.

Solution: Serilog captures structured message templates and named properties. The current file sink in Program.cs writes formatted text to logs/app-.log, not JSON, while preserving structured templates for sinks that support property queries.

// Plain text log (hard to query):
"User admin@company.com failed login from 172.16.3.50 at 2026-04-23T14:30:00Z"

// Serilog message template used by the application:
_logger.LogWarning("Failed login for {UserId} from {IpAddress}",
    userId, ipAddress);

// Current file sink output format:
2026-04-23 14:30:00.000 +00:00 [WRN] Failed login for admin@company.com from 172.16.3.50

Why This Matters:

  • Rolling file sink: Logs rotate daily and retain the last 30 files, matching the Serilog file sink configuration in Program.cs.
  • Request pipeline integration: Serilog's ASP.NET Core middleware logs dynamic requests that pass through UseSerilogRequestLogging() with status code, duration, and path.
  • Performance monitoring: The PerformanceBehavior uses Serilog to flag slow MediatR operations with structured data for easy identification.

Why SQLite? — Zero-Configuration Deployment

Problem: This is an internal enterprise tool deployed on a single Windows server. Installing and maintaining SQL Server or PostgreSQL adds operational complexity (DBA requirements, backup agents, licensing costs, network configuration) that is disproportionate to the system's scale.

Solution: SQLite is an embedded database that lives as a single file (App_Data/IT_FormDB.db). It requires zero installation, zero configuration, and zero maintenance beyond file-level backups (handled by DatabaseBackupService).

Tradeoffs Accepted:

  • Single-writer: SQLite uses file-level locking, limiting write concurrency. This design fits the current single-server internal portal; higher write concurrency would require moving to a client/server database.
  • No network access: The database is local-only. Multi-server deployments would require migration to PostgreSQL — but this system is designed for single-server operation.
  • Backup simplicity: The DatabaseBackupService copies the entire DB file with a timestamp. Restore = copy the file back. No pg_restore or .bak files to manage.

2.1 Authentication Mechanisms

Password Hashing — Argon2id

Replaces the default ASP.NET Identity PBKDF2 hasher with Argon2id (memory-hard, side-channel resistant).

Code Example: Argon2idPasswordHasher.cs

The hasher uses a self-describing binary format that embeds all parameters in the hash output, enabling transparent parameter upgrades.

public string HashPassword(TUser user, string password)
{
    byte[] salt = RandomNumberGenerator.GetBytes(_settings.SaltSize);
    byte[] hash = ComputeHash(password, salt, _settings);

    // Binary: [marker:1][parallel:1][memory:4][iter:4]
    //         [saltLen:2][hashLen:2][salt:N][hash:N]
    byte[] result = new byte[14 + _settings.SaltSize + _settings.HashSize];
    result[0] = 0x02;  // Versioned format marker
    result[1] = (byte)_settings.DegreeOfParallelism;
    BinaryPrimitives.WriteInt32LittleEndian(
        result.AsSpan(2), _settings.MemorySize);
    // ... salt and hash appended after 14-byte header
    return Convert.ToBase64String(result);
}

public PasswordVerificationResult VerifyHashedPassword(
    TUser user, string hashedPassword, string providedPassword)
{
    byte[] decoded = Convert.FromBase64String(hashedPassword);

    // 1st: Try current versioned Argon2id (0x02)
    if (TryVerifyVersionedArgon2(decoded, providedPassword, out var r))
        return r;

    // 2nd: Try legacy Argon2id (0x01) — rehash on success
    if (TryVerifyLegacyArgon2(decoded, providedPassword, out r))
        return r;  // Returns SuccessRehashNeeded

    // 3rd: Fallback to ASP.NET Identity PBKDF2
    var fallback = _fallbackPasswordHasher
        .VerifyHashedPassword(user, hashedPassword, providedPassword);
    return fallback switch
    {
        PasswordVerificationResult.Success =>
            PasswordVerificationResult.SuccessRehashNeeded,
        PasswordVerificationResult.SuccessRehashNeeded =>
            PasswordVerificationResult.SuccessRehashNeeded,
        _ => PasswordVerificationResult.Failed
    };
}

private static byte[] ComputeHash(string password,
    byte[] salt, Argon2idSettings s)
{
    using var argon2 = new Argon2id(Encoding.UTF8.GetBytes(password))
    {
        Salt = salt,
        DegreeOfParallelism = s.DegreeOfParallelism,  // 4
        MemorySize = s.MemorySize,                      // 32 MB
        Iterations = s.Iterations                       // 3 passes
    };
    return argon2.GetBytes(s.HashSize);                 // 32 bytes
}

How It Works:

  • Self-describing format: The hash embeds all Argon2id parameters (parallelism, memory, iterations, salt/hash sizes) in the binary output. This means the system can verify hashes created with any past parameter set without configuration lookups.
  • Three-tier verification: On login, the hasher tries (1) current v2, (2) legacy v1, (3) PBKDF2 fallback. Any success with older formats returns SuccessRehashNeeded, prompting the system to transparently re-hash with current settings.
  • FixedTimeEquals: Hash comparison uses constant-time comparison to prevent timing side-channel attacks.

2.3 Cryptographic Implementations

HMAC-SHA256 Signature Integrity (H-03)

Prevents tampering of digital signature images. When a user signs a form, SignatureIntegrityService computes an HMAC over the canonical signing event data:

Canonical Message = "{EntityType}|{EntityId}|{SignerUserId}|{SignedAtUtc:O}|{SignatureBase64}"
Algorithm        = HMAC-SHA256
Key Source       = Environment variable IT_FORM__SignatureHmac__Key (Base64-encoded; deploy with >=32 random bytes)
Output           = Uppercase hex string stored alongside signature in DB
Verification     = Constant-time comparison via CryptographicOperations.FixedTimeEquals()

Legacy system-imported signatures are prefixed SYSTEM-IMPORT- and trusted by default.

Code Example: SignatureIntegrityService.cs — HMAC Anti-Tampering

This service addresses Audit Finding H-03: preventing a rogue admin from swapping one digital signature image for another without detection.

public class SignatureIntegrityService : ISignatureIntegrityService
{
    private readonly byte[] _keyBytes;

    public SignatureIntegrityService(IConfiguration configuration)
    {
        var keyStr = configuration["SignatureHmac:Key"];
        if (string.IsNullOrWhiteSpace(keyStr) ||
            keyStr.Contains("SET_VIA_ENV_VAR"))
            throw new InvalidOperationException(
                "SignatureHmac:Key is not configured.");

        _keyBytes = Convert.FromBase64String(keyStr);  // Deployment should use >=32 bytes
    }

    public string ComputeHmac(string entityType, string entityId,
        string signerUserId, DateTime signedAtUtc, string signatureBase64)
    {
        // Fix DateTimeKind loss from SQLite (strips trailing 'Z')
        var normalizedDate = DateTime.SpecifyKind(signedAtUtc, DateTimeKind.Utc);

        // Pipe-delimited canonical message prevents concatenation attacks
        var message = $"{entityType}|{entityId}|{signerUserId ?? ""}|" +
                      $"{normalizedDate:O}|{signatureBase64}";

        using var hmac = new HMACSHA256(_keyBytes);
        var hashBytes = hmac.ComputeHash(Encoding.UTF8.GetBytes(message));
        return Convert.ToHexString(hashBytes);  // Uppercase hex: "A1B2C3..."
    }

    public bool Verify(string entityType, string entityId,
        string signerUserId, DateTime signedAtUtc,
        string signatureBase64, string storedHmac)
    {
        if (string.IsNullOrEmpty(storedHmac)) return false;

        // Legacy Excel imports are trusted
        if (storedHmac.StartsWith("SYSTEM-IMPORT-")) return true;

        try
        {
            var computed = ComputeHmac(entityType, entityId,
                signerUserId, signedAtUtc, signatureBase64);

            // Constant-time comparison prevents timing side-channel attacks
            return CryptographicOperations.FixedTimeEquals(
                Convert.FromHexString(computed),
                Convert.FromHexString(storedHmac));
        }
        catch (FormatException)
        {
            return false;
        }
    }
}

How It Works:

  • Pipe delimiter (|): Prevents concatenation ambiguity attacks — e.g., "UserA|1" vs "UserA1|". All five fields are included so changing any field invalidates the HMAC.
  • DateTime normalization: SQLite strips the UTC Z suffix from ISO-8601 dates. DateTime.SpecifyKind restores it to ensure the canonical message matches between sign-time and verify-time.
  • FixedTimeEquals: Uses CryptographicOperations for constant-time comparison, preventing an attacker from deducing valid HMAC bytes through response timing analysis.
  • SYSTEM-IMPORT- prefix: Legacy records imported via Excel bulk upload don't have valid HMACs. The prefix bypasses verification for these specific records only.

public class SecurityHeadersMiddleware

Code Example: AuditLoggingBehavior.cs — Automatic Command Audit Trail

This MediatR pipeline behavior captures a structured audit log for every Command operation, recording actor, IP, payload, and success/failure status — without requiring manual logging in handlers.

public sealed class AuditLoggingBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
{
    public async Task<TResponse> Handle(TRequest request,
        RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        if (!ShouldAudit(request)) return await next();

        var action = request.GetType().Name;  // e.g. "ProcessOnboardingSignatureCommand"
        var userId = _httpContextAccessor.HttpContext?
            .User?.Identity?.Name ?? "System";
        var payload = JsonSerializer.Serialize(request);
        var correlationId = Guid.NewGuid();   // Links related audit entries

        try
        {
            var response = await next();      // Execute the command handler

            await WriteSuccessAuditLogAsync(new AuditLog
            {
                UserId = userId, Action = action, Payload = payload,
                IsSuccess = true,
                IpAddress = _httpContextAccessor.HttpContext?
                    .Connection?.RemoteIpAddress?.ToString(),
                CorrelationId = correlationId
            }, ct);

            return response;
        }
        catch (Exception ex)
        {
            // Uses separate DbContext scope to survive txn rollback
            await WriteFailureAuditLogAsync(new AuditLog
            {
                UserId = userId, Action = action, Payload = payload,
                IsSuccess = false, ErrorMessage = ex.Message,
                CorrelationId = correlationId
            }, ct);

            throw;  // Re-throw for TransactionBehavior rollback
        }
    }

    // Only audit Commands, not Queries
    private static bool ShouldAudit(TRequest request)
        => request.GetType().Name.EndsWith("Command");
}

How It Works:

  • CorrelationId: A unique Guid links all audit entries generated during a single request. The UI's "Audit Chain" view uses this to show the full lifecycle of a command.
  • Failure isolation: Failed command audits use a separate DbContext scope (IServiceScopeFactory) so the failure audit survives even when the main transaction rolls back.
  • Convention-based: Only types ending in *Command are audited. Query operations are excluded to reduce audit noise.
