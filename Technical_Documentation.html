Section 1

1. Architecture Overview

The system combines Clean Architecture and Vertical Slice Architecture. Clean Architecture defines dependency boundaries, while Vertical Slice Architecture organizes business behavior by use case. The result is a codebase where controllers stay thin, handlers stay focused, and workflow rules stay close to the domain objects that own them.

The dominant execution path is request driven: MVC endpoints receive the HTTP request, dispatch a command or query through MediatR, run pipeline behaviors, execute the feature handler, and then return a view or redirect. Legacy MVC-style code still exists in some areas, but the main application path is already slice oriented.

Architectural Positioning
This is not a classic layered monolith where all business logic sits in a single service layer. Instead, business logic is distributed into feature slices under Application/Features, which reduces cross-feature coupling and makes use cases easier to trace.
Clean Architecture role

Separates presentation, application, domain, and infrastructure so business code is not forced to depend on delivery or persistence details.

Vertical Slice role

Groups handlers, validators, mapping, and result models by feature so changes are localized to the use case being modified.

2. Clean Architecture and Vertical Slice Design

2.1 Clean Architecture boundaries

The system uses clear dependency direction. Controllers depend on application requests, handlers depend on domain and infrastructure abstractions, and infrastructure implements technical concerns such as persistence and email. This keeps the business path testable and reduces the chance of presentation concerns leaking into domain logic.

  • Presentation stays thin and should mostly decide how to expose the result.
  • Application owns orchestration and is the home of use-case specific logic.
  • Domain owns state changes such as workflow transitions.
  • Infrastructure provides the technical building blocks without owning the business process itself.

2.2 Vertical Slice organization

Instead of a large shared service layer, each feature keeps the pieces required for that use case together. That typically includes a command or query contract, a handler, validators, result models, and any slice-specific mapping or flow helpers.

2.3 Stateful domain workflow with Stateless

Models/OnboardingRequest.cs uses a Stateless state machine rather than treating workflow status as a passive field. The entity exposes methods such as SubmitByHr(), StartItSetup(), FinishOnboarding(), and Cancel(), so legal transitions are enforced close to the aggregate. 

private void ConfigureStateMachine()
{
    _machine.Configure(RequestStatus.Draft)
        .Permit(OnboardingTrigger.SubmitByHr, RequestStatus.PendingITApproval)
        .Permit(OnboardingTrigger.Cancel, RequestStatus.Rejected);

    _machine.Configure(RequestStatus.PendingITApproval)
        .PermitReentry(OnboardingTrigger.StartItSetup)
        .Permit(OnboardingTrigger.FinishOnboarding, RequestStatus.PendingEmployeeSign)
        .Permit(OnboardingTrigger.Cancel, RequestStatus.Rejected);
}

The domain also projects multiple stored statuses into business-friendly abstract states. This is how the system can present a simpler business workflow while still storing more detailed execution statuses internally.

Abstract state Stored status examples Interpretation
Draft Draft HR is still preparing the request.
HrSubmitted PendingITApproval, PendingApproval, PendingHRApproval, PendingHODApproval HR input has been submitted and the request is waiting for the next operational step.
ItProvisioning PendingITApproval with recorded IT progress IT has started work, even though the persisted status remains inside the same phase.
Completed PendingEmployeeSign, Approved, Completed The business work is complete and the request is in final acknowledgement or closure steps.
Canceled Rejected The workflow has been stopped intentionally.

3.1 MediatR and CQRS

The application models reads as queries and writes as commands. Controllers do not call domain services directly for most mainline use cases. Instead they send requests through MediatR, which keeps feature logic behind one execution path and makes cross-cutting concerns consistent. 

builder.Services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssemblyContaining<Program>();
    cfg.AddOpenBehavior(typeof(ValidationBehavior<,>));
    cfg.AddOpenBehavior(typeof(AuditLoggingBehavior<,>));
    cfg.AddOpenBehavior(typeof(TransactionBehavior<,>));
    cfg.AddOpenBehavior(typeof(RequestLoggingBehavior<,>));
    cfg.AddOpenBehavior(typeof(PerformanceBehavior<,>));
});
Pipeline behavior Purpose Practical effect
ValidationBehavior Runs validators before the handler Rejects malformed requests early.
AuditLoggingBehavior Captures success and failure around request execution Adds request-level traceability alongside entity audit logs.
TransactionBehavior Wraps write operations in a database transaction Commits atomically for command requests and skips import handlers that manage their own transactions.
RequestLoggingBehavior Logs request start and completion Makes production traces easier to correlate.
PerformanceBehavior Measures slow requests Surfaces handler latency that deserves investigation.

3.2 Mapster

Mapster is registered centrally through MapsterConfig.RegisterMappings(). The configuration enables case-insensitive member matching and default IgnoreNullValues(true), which makes update mappings safer for partial writes while still allowing specific mappings to opt out when required.

  • Entity-to-view-model mappings support dashboards, editor pages, and list queries.
  • Write-model mappings explicitly ignore identifiers, password hash fields, and heavy navigation collections where needed.
  • The mapping layer is kept in application space rather than scattered across controllers.

3.3 FluentValidation

Validators are discovered from the assembly and executed inside the MediatR pipeline. Handlers can therefore focus on orchestration, persistence, and business decisions instead of repeating input guards. 

var context = new ValidationContext<TRequest>(request);
var results = await Task.WhenAll(
    _validators.Select(v => v.ValidateAsync(context, cancellationToken)));

var failures = results
    .SelectMany(r => r.Errors)
    .Where(e => e != null)
    .ToList();

if (failures.Count > 0)
{
    throw new ValidationException(failures);
}
